# 大巴扎 (The Bazaar) 核心玩法与优质阵容搜索

本项目是游戏《大巴扎》（The Bazaar）的模拟对战测试平台和优质阵容探测器。
本文档概述基础规则、搜索问题的形式化描述、判定难点，以及对「下一步算法」的理解与建议（供后续设计讨论；不绑定既有 GDF / GDF-PA 实现）。

## 基本规则

《大巴扎》是一个 PVP 自走棋游戏。每名玩家最多有从左到右的 10 个格子，用来放置物品。一个物品可能占据 1、2 或 3 个格子（称为小型、中型和大型物品）。因此玩家实际放置在阵容中的物品数量通常在 4 到 10 之间。玩家在进入对战之前可以随意移动物品次序。

> 实际游戏中存在玩家等级的概念，玩家等级会影响玩家的初始生命上限和格子的数量。在我们的项目中通常会固定玩家的等级，在相同等级下进行模拟对战测试和优质阵容探测。

每个物品可能有主动效果、被动效果和光环效果。

- 主动效果（在物品描述里用“▶”开头的行）：游戏开始后物品开始读秒充能（按照冷却时间），充能满之后“使用物品”，触发一定的效果。
- 被动效果：在满足某些条件（除“使用物品”外）时会触发对应的效果，例如“敌方使用物品时，造成 1 伤害”。
- 光环效果：自动生效（而非触发）的效果，例如“己方武器的伤害 +1”。

游戏对战过程发生在两名玩家之间，自动进行所有战斗，中途没有玩家操作。
因此，我们希望基于本项目的高性能模拟对战测试平台，去搜索哪些阵容是优质阵容。

## 形式化的搜索任务描述

给定格子数量 $N\le 10$（通常是 10，也有可能是 6 或 8）和候选物品集合$S=\{S_1,S_2,\dots,S_K\}$，其中物品数量$K\approx 100$。
每个候选物品$S_j$具有物品大小$t_j\in\{1,2,3\}$。

搜索范围（候选阵容）为所有的序列$X=(S_{x_1},S_{x_2},\dots)$，其中$\sum_k t_{x_k} = N$。

判定器（即模拟对战测试）可以比较序列$X=(S_{x_1},S_{x_2},\dots)$和$Y=(S_{y_1},S_{y_2},\dots)$的对战结果。

## 关键约束

- 阵容里物品的大小总和等于玩家的格子数量。
- 阵容里物品的位置会影响效果（部分效果如“加速左侧的物品”）。
- 对战存在随机性（暴击等），相同阵容在不同随机种子下的对战结果可能不同。
- 对战可能平局（同一帧双方的生命值同时降到0或0以下），通常需要用额外判别（比如生命更接近 0 的获胜）。
- 不同风格的阵容存在克制关系，即对战得到的“相对强度”不具有传递性。
- 随机阵容强度极低，不具有参考价值。

## 来自实际游戏的启发式经验

在实际游戏中，虽然完整的候选物品集合很大（$K\approx 100$），但在给定的等级下，通常只有很少的一部分物品“好用”，而大部分物品要么完全“不好用”，要么只有在极少的阵容配合下“好用”。

关于物品次序：物品描述通常会写清左右位依赖；在大部分情况下，许多“交换次序”在机制上完全等价。若仅用有限局数的对战来比较等价排列，随机性容易制造虚假的强度差。

## 问题理解：难点到底在哪里

「找优质阵容」看起来像组合优化，真正难的是下面几层叠在一起：

1. **组合爆炸**：在尺寸约束下从约百件物品中选有序序列，空间极大；且强度依赖高阶协同（往往需要 A+B+C 同时出现），不是单件边际增益可加。
2. **非传递克制**：相对战力不是全序。不存在稳定的标量「绝对强度」能同时服务所有对局；rock-paper-scissors 式生态是常态。
3. **「较好」难以分界**：几乎所有稍像样的阵都能对随机阵接近百分百胜率。有参考意义的强度，必须定义在「已经足够强的对手集合」上——但这个集合本身正是搜索要发现的对象，形成循环依赖。
4. **排列评估贵且噪声大**：同物品多重集下的最佳站位值得找，但全靠系列赛比较排列，既耗评估预算，又容易被 RNG 带偏。
5. **稀疏可用性**：池子虽大，有效物品与有效配合很少；对全池一视同仁会把预算浪费在明显无效的分支上。

因此，缺的往往不是「更好的局部搜索超参」，而是一个在非传递、噪声 oracle 下仍然有意义的**解概念**（什么叫优质），以及与之匹配的外环算法。

## 既往路径与边界（教训）

以下做法已在本项目中尝试或接近触顶，作为边界认知保留；新算法不必再沿同一哲学加补丁。

- **随机起点的遗传 / 局部爬山**：对战噪声大，适应度不稳定；收敛时间难控，结果可复现性差。
- **固定种子、按占用格数递增的贪心扩展（GDF 一类）**：擅长「单核 / 少核向外长」；难以一次引入必须成套的 A+B+C；与「天平」等强依赖物品数量奇偶的机制冲突。同组合下多插入位循环赛是主要时间开销之一。锚点边际、多样性惩罚、泛用度（GDF-PA）等可改善排序与汇报，但难以突破上述结构上限。
- **相对随机或相对「同一次 beam 内全体」的胜率**：前者无区分度；后者容易内卷成同构变体，且仍未回答「较好」的外部分界。

结论：增量式贪心扩展 + 瑞士/循环赛选优，已经把「局部可扩展的强核」榨得较充分；继续堆叠同一框架的边际收益有限。更需要的是换问题定义，而不是换一个搜索器外壳。

## 解概念：什么叫「优质」

不建议再追求单一的「绝对最强阵」。更站得住的解概念包括：

- **近似 Nash 支撑**：把可表示阵容空间看成巨大矩阵博弈；优质阵容 ≈ 当前策略池上混合均衡里权重显著的纯策略，或能显著剥削该均衡的 best response。
- **生态位上的精英**：在行为/风格描述子空间中，各格子上相对其他强者仍站得住的代表阵（质量-多样性），强调覆盖可玩克制环，而非塌缩成一份同构 Top-K。

「打赢随机」和「仅在同批候选里内卷排序」都不应作为最终目标函数。Meta（或归档精英集）本身就是「较好」的操作化定义，并应随发现更新。

## 算法建议（大方向）

下列路线刻意抛开「锚点 → 逐 size 贪心 → 瑞士/循环赛 Top-K」主流程；最多复用模拟器与阵容构建，不继承其搜索哲学。

### 路线 A：元博弈 / PSRO（优先推荐）

将任务改为在阵容空间上逼近 Nash（Policy-Space Response Oracles / Double Oracle 一类）：

1. 维护策略池 $P=\{d_1,\dots,d_m\}$（有序阵容）。
2. 用多 seed 模拟填充 $P\times P$ 收益矩阵。
3. 求混合 Nash $\sigma$，监控支撑集与 exploitability。
4. 针对 $\sigma$（或当前 meta）做 **best response** 搜索，得到新阵 $d^*$；若能稳定剥削则并入 $P$，迭代。

含义上的变化：

- 「优质」= 均衡里站得住，或能打破当前均衡——天然容纳克制环。
- 不再人为划「较好阵容」硬阈值；meta 即分界。
- A+B+C、奇偶敏感构筑只需在某次 best response 中被找到即可进池，不依赖 size 单调构造。

Best response 子问题仍难，但目标变为「打固定（混合）对手」，比「在全体中找全局最优」干净。可用带结构性 jump 的进化 / MCMC / 其他强局部搜索专打 $\sigma$。初始 $P$ 需要风格多样的冷启动，而非单一贪心流水线产物。

### 路线 B：质量-多样性（MAP-Elites 味）

不为单一标量优化，而在**行为描述子**网格上每格保留精英。描述子宜来自战报画像（输出构成、节奏/中位击杀帧、关键机制密度、站位相关统计等），避免只用物品名 Jaccard。变异算子应支持整组替换、核心多件插入，以及对奇偶敏感物品的专项扰动。适应度取「相对档案中其他精英」或「相对当前 meta」的胜率。

产物是一张风格覆盖图，可直接作为路线 A 的初始策略池或持续的多样性前端。

### 路线 C：机制先验 + 学习替代模型（算力结构升级）

1. 从物品描述/效果结构抽取协同图，用符号或图枚举闭环骨架，缩小组合层提议。
2. 用自对弈数据训练双阵容胜率替代模型；排列层用规则剪枝等价置换 + 少量真打消歧。
3. 内环用替代模型做大规模提议，外环用真模拟器校准并挖掘反例。

目标是把真模拟器从「每次提议的内环」提升到「校准与对抗生成的外环」，数量级地提高有效搜索次数。风险是替代模型的系统性盲区，必须靠外环纠偏。

### 推荐组合形态

- **主解概念与外环**：路线 A（元博弈 / PSRO）。
- **策略发现与覆盖**：路线 B 作为生成与多样性前端。
- **加速**：路线 C 作为 best response 与矩阵填充的加速器（可后置）。

池收缩与协同先验（「多数物品本等级不好用」）应作为任意路线的前置层，但这是搜索预算分配，不是解概念本身。

## 排列与噪声（横切原则）

无论采用哪条主路线，建议将「选组合（多重集 / 骨架）」与「排次序」解耦：

- 组合层负责协同与对抗 meta；
- 排列层优先用机制/描述做等价类合并，只对歧义排列拨打真模拟；
- 多 seed 下置信区间重叠则视为无差异，避免虚假优选吞掉评估预算。

## 仍待拍板

新系统的主产物形态会影响指标与工程边界，例如：

- 近似 Nash / meta 混合（代表阵 + 权重 + exploitability）；
- 风格覆盖图（多生态位精英）；
- 或以 Nash 为主、覆盖图为前端的组合形态。

本文只固定问题理解与方向性建议；具体系统设计（数据结构、冷启动、停止准则、与现有 CLI/引擎的边界）另开设计文档讨论。
